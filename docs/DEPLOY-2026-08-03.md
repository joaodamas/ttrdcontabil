## O que ainda BLOQUEIA (só o dono resolve)

### 1. `SPEDY_WEBHOOK_SECRET` não provisionado — bloqueia o deploy inteiro

`functions/src/nfse/webhook-spedy.ts:61` declara o secret, e a function **é**
exportada no `index.ts`. O CLI do Firebase resolve secrets na fase de análise,
**antes** de filtrar por `--only` — então até um deploy de uma função só aborta.

Secrets declarados no código × existentes no projeto (verificado em 03/08):

| Secret | No código | No projeto | Bloqueia? |
| --- | --- | --- | --- |
| `CREDENTIAL_KEY` | sim | **sim** | não |
| `SMTP_USER` / `SMTP_PASS` | sim | **sim** | não |
| `SPEDY_WEBHOOK_SECRET` | sim (export ativo) | **NÃO** | **SIM** |
| `SPEDY_OWNER_API_KEY` | sim | não | não — mora em `provisionar-spedy.ts`, cujo export está comentado |
| `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` | sim | não | não — `whatsapp/core` só entra por `await import()` dinâmico em `triggers/cliente-events.ts`, de propósito |

O segredo é **compartilhado, inventado por nós** — não se busca na Spedy.
`conferirCredencialWebhook` (`provedores/spedy-evento.ts:294`) aceita dois modos:
HMAC-SHA256 do corpo bruto (headers `x-spedy-signature` / `x-signature` /
`x-hub-signature-256`) ou token simples (`x-spedy-token` / `x-webhook-token` /
`?token=`).

```
openssl rand -hex 32
firebase functions:secrets:set SPEDY_WEBHOOK_SECRET
```

Depois, cadastrar no painel da Spedy a URL de callback:

```
https://southamerica-east1-ttrdcontabil-jpproject.cloudfunctions.net/webhookSpedy?token=<valor>
```

(sem `?token=` se usar o modo assinatura)

## Ordem do deploy

Regras e índices primeiro, functions depois, hosting por último: as regras novas
exigem `sameTenantExisting()`, e subir a UI antes das regras deixaria a tela
pedindo o que o banco ainda nega.

```
# 1. pré-voo
git fetch && git status                    # limpo e em dia com o origin
npx vitest run                             # 230
npx firebase emulators:exec --only firestore --project ttrdcontabil-rules-test \
  "npx vitest run __tests__/rules"         # 67

# 2. secret (bloqueante)
firebase functions:secrets:set SPEDY_WEBHOOK_SECRET

# 3. regras + índices
firebase deploy --only firestore:rules,firestore:indexes

# 4. functions (lê a lista de remoção antes de confirmar)
firebase deploy --only functions

# 5. hosting
firebase deploy --only hosting
```

`firebase.json` tem predeploy com `npm run build` em `functions` e `hosting` —
não precisa buildar à mão.

Os índices são a maior mudança silenciosa deste deploy (`firestore.indexes.json`,
+1743 linhas). **Índice novo não fica pronto na hora**: o Firestore constrói em
segundo plano e a query falha com `FAILED_PRECONDITION` enquanto isso. Acompanhe
no console antes de considerar o deploy concluído.

## Por que isso não foi feito ANTES da 1ª emissão real

Decisão de 03/08: emitir a primeira nota real com o código atual (anterior a
29/07) e deployar depois. O código em produção **não tem** a idempotência
(`integrationId`, `buscarNotaPorIntegrationId`, `ehTransitorio` — commit
`b95bce5`, 29/07), então um polling que estoura + clique em reemitir gera nota
duplicada na prefeitura. A mitigação escolhida foi operacional: emitir uma vez e,
diante de `SPEDY_PROCESSANDO`, conferir no painel da Spedy em vez de clicar em
retry. Deployar 15 commits não homologados minutos antes de uma emissão fiscal
real trocaria um risco conhecido por vários desconhecidos.
